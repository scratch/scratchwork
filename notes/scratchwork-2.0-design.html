Scratchwork 2.0

A shared workspace where people and agents write and publish documents together. You write and share like in Google Docs, and agents can still use everything HTML and JS can do.

What we want to be able to do

  1. Use my own agent (e.g. Claude Code) to create and publish documents made of any HTML and JS.
  2. Use an agent built into the web app to create or edit a document live.
  3. Write and edit the text in my documents by hand, including in documents an agent built.
  4. See where other people are editing in real time.
  5. See where agents are editing in real time.

Starting point

Scratchwork 1 already covers item 1: scratchwork dev / publish, a Markdown renderer that supports React components, project roles (read / write / admin), and servers that run on Cloudflare, AWS, and locally. What it doesn't have is live editing. Documents are static files, and republishing replaces the whole file.

The hard part is item 3. Past editors worked because they owned a narrow format (Word, Docs). Here, an agent writes the document as arbitrary code, and a person still needs to edit its text without breaking it.

Working model

This is a straw man to react to, not a decision. It splits every document into two layers that change in different ways:

document
├── code    HTML / JS / components     written by agents, saved as whole versions
└── text    named text regions          edited live by people + agents (CRDT)

rendered page = code, with each text region filled in from the live text

The code declares where the editable text goes. The editor only touches those regions, so hand edits can't produce broken code. Agents can edit either layer. People mostly edit text.

Decisions

Open not discussed yet Leaning has a tentative answer Decided settled

D1 How does a document expose editable text?

Open
  • AMDX-style. Markdown prose with embedded components. The prose is editable and text inside components isn't. Builds on the renderer we already have, but agent-made HTML pages don't fit.
  • BMarked regions. Any HTML page marks editable text with an attribute like data-sw-text="intro". The editor owns those regions. Works for any page, but agents have to follow the convention, and we need a validator.
  • CExported data. The document exports a structure of strings (like a content file) and renders from it. Very robust, but the most work for agents, and inline editing on the page is harder.

Claude's leanB, with A as sugar on top: Markdown prose becomes one large marked region automatically, so Markdown documents need no extra work.

D2 How are conflicting edits resolved?

Open
  • ACRDT for text, versions for code. Text regions use a CRDT (e.g. Yjs), so concurrent edits merge on their own. Code changes are saved as whole versions. If two conflict, the later one is rebased or rejected.
  • BAn arbiter agent for everything. An agent merges conflicting edits. Flexible, but slow and nondeterministic, and it's in the path of every keystroke.
  • CA (deterministic) plus an arbiter only for code conflicts.

Claude's leanC. Typing must never wait on a model. Notion's CRDT write-up shows the text side works at scale.

Pete—

D3 Where does real-time sync run?

Open
  • ACloudflare-first. One Durable Object per document holds the WebSocket connections, orders edits, and saves snapshots. It's the simplest fit, but the AWS and local servers would fall behind in features, which breaks today's rule that every deploy target behaves the same.
  • BA sync interface for every target. Define a sync service and implement it for Cloudflare (Durable Objects), local (an in-process Bun server), and AWS (API Gateway WebSockets). Keeps the targets equal, but it's roughly three times the work.
  • CA hosted sync service (Liveblocks, PartyKit, etc.). Fastest to ship, but adds an outside dependency and makes self-hosting harder.

Claude's leanB's interface with only A implemented at first. Local dev gets an in-memory version so tests stay hermetic. AWS waits until someone needs it.

Pete—

D4 How do outside agents work with documents?

Open
  • ACLI only. Extend scratchwork with commands like edit, pull, and watch.
  • BMCP only.
  • CBoth, as thin layers over one HTTP API defined in shared/ like today's publish API.

Claude's leanC. The built-in agent should use the same API, so it can't do anything an outside agent can't.

Pete—

D5 What does "seeing where an agent is editing" look like?

Open
  • AA cursor, like a person's. The agent streams small edits into text regions, and you watch it type.
  • BRegion highlights. Show which region or component the agent is working in ("Claude is editing Pricing"), then apply its changes as one reviewable change.
  • CSuggestions. Agent edits show up as tracked changes that a person accepts.

Claude's leanB by default, with C as a per-document setting. Watching an agent type feels good, but it's noisy and hard to undo.

Pete—

D6 Is this Scratchwork 2.0 or a new product?

Open
  • AGrow Scratchwork. Keep the CLI, server, and renderer, and add documents, sync, and an editor.
  • BA new product ("Writer") that reuses Scratchwork's pieces as libraries.

Claude's leanA. Auth, roles, publishing, and the deploy targets are most of the backend already. The existing roles map to read / write / owner, and "at least one owner" becomes a server-side rule.
