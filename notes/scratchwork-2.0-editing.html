Editing rendered documents

People edit the manuscript of an agent-built document on the rendered page, live with other viewers, and the edits land in the source files. Everything else is app logic, which agents edit in the files.

Principles

  • Standardize as little as possible. No document format. An agent can still invent its own conventions (e.g. --- between slides).
  • Edit the rendered page, not the source. Source files are for agents.
  • Manuscript is hand-editable. App logic isn't. Text in a widget's JS is changed by asking an agent.
  • No model in the editing loop. Mapping is deterministic, merging is a CRDT, typing never waits.

Manuscript and app logic

A document has two kinds of text:

  • Manuscript is text in vanilla HTML elements that roughly match what Markdown expresses: headings, paragraphs, list items, blockquotes, table cells, code blocks, and inline emphasis, links and code. It is written as plain HTML or Markdown, and people edit it on the rendered page.
  • Hello
  • App logic is everything else: JS, components, SVG, canvas, and any string in code or built at runtime. Agents edit it in the files.

The test is mechanical: an element is manuscript if a deterministic parse of the source finds its text at a known position. Text that JS created or changed fails the test and is locked. Clicking it does nothing in v1; later it can open the embedded agent with that text as context.

How an edit works

Mechanics

  • Parse. On load, a deterministic parser walks the source (HTML, or Markdown we render), numbers the manuscript elements in document order, stamps each with data-sw-id, and records the source range of every text node inside it.
  • Map. An edit to a stamped element is diffed against its indexed text and becomes the smallest character change to those ranges. Only text nodes are spliced; tags and attributes stay byte-for-byte identical, so inline <em> and <a> survive.
  • Lock. Elements without an id, or whose text no longer matches the index when clicked, are not editable.

  • Sync. Every file is a Yjs Y.Text; all of a document's files share one Yjs document and one connection. Only file changes cross the network. Browsers re-parse and re-render; the CLI writes changes to disk and diffs local saves back. One mechanism covers concurrent typing, offline edits and edits made on disk.
  • Server. Orders changes, keeps the log, saves snapshots so new page requests get current source.

Prototype. bun wip/editor/open.ts ./site opens a folder or file in the page editor: the parse, the mapping, the in-place editing, disk save and disk watch, for HTML and Markdown. No sync yet; the host is Effect on Bun, the browser core plain TypeScript pending D1.

Decisions

D1Is the core plain TypeScript or Effect?

Decided

The viewer runtime is injected into every published page. Measured with bun build --minify, Effect 3.22: a minimal Effect.gen + runSync program is 39 KB gzipped, 51 KB with Schema. Yjs alone is 23 KB; today's renderer is 75 KB. Effect adds real weight, but not enough to justify a second exception to invariant 1.

DecidedEffect everywhere, including the browser core. Keep the viewer bundle measured in the gate.

D2Where does ordering and sync run?

Decided

One sync interface with identical observable behavior on every target (invariant 6), proven by a shared conformance suite.

DecidedDurable Objects on Cloudflare, plus an in-memory local implementation. AWS gets its own implementation of the same interface later.

D3Which elements are manuscript?

Decided

The Markdown list (p, h1–h6, li, blockquote, td/th, pre, inline em, strong, a, code) plus div and span, judged by a deterministic text-likeness rule: an element is text-like if its children are text and inline elements (a leaf), or if all its element children are text-like blocks (a container, like a div of paragraphs). Grow the list by adding elements.

DecidedMarkdown list + div/span, with the text-like rule. The exact rule is worked out in code.

D4Are styles and structural edits in scope?

Decided

Inline styles (bold, italic, links, code) and structure (new paragraph, list item, heading) are spelled differently in HTML and Markdown. Manuscript has only those two spellings, so both can be implemented without per-document hints.

DecidedYes to both. Text splicing ships first; styles and structure follow for both source spellings.

D5How do agent file edits and live edits coexist?

Leaning

An agent that rewrites a file (or a republish from disk) is diffed into changes and merged by the CRDT like any other edit, however large. The risk is a large diff colliding with concurrent live edits and producing broken markup.

LeanMerge consistently by default. Detect when a publish's diff collides with concurrent edits beyond a threshold and reject it. A publish can optionally take a lock on the document, in which case live edits are rejected instead. The threshold and lock semantics are open.

D6How are the editor and page JS isolated?

Decided

Agent-written JS must not have the editor's write access.

DecidedThe page runs in a sandboxed iframe; contenteditable and edits cross a narrow postMessage bridge.

D7Which CRDT, and how does undo work?

Decided

Building our own is tempting but premature. Yjs at defaults covers text merging, one document per doc, and per-origin undo via UndoManager.

DecidedYjs at defaults, including UndoManager scoped to your own edits. Revisit building our own only if defaults prove wrong.
